## Context

动机见 proposal.md 的 Why 一节，行为要求见 `specs/`。这里只记录影响做法的现状。

- 核心层 `src/core` 不认识任何托管。Source 通过 `SourceKind`（`src/sources/kind.ts`）接入，飞书已经是一个与 GitHub 平级的 Source。
- GitHub 渗进通用代码的位置已列在 `docs/007-architecture.md` 的 "Source-specific dependencies" 一节，具体如下：
  - `Deployment` 里写死了 `repository`、`github: {cli, login, noreply}`，由 `resolveDeployment` 解析；
  - `Commands.api` 和 `Commands.pages` 只走 `gh api repos/<repo>/…`；
  - `writeEnvironment` 和 `verifyEnvironment` 只写、只检查 `gh` shim 与 github.com 的凭据；
  - `ExecutorToolsHost.github`，加上 `readPull`、`claimPull` 和 `pr_number`；
  - `pullEndNotices`、`pullOf`、`readRepositoryPath`、`readGithub`；
  - `bundledSkills`、`sourceSkills`、`PART_KEYS` 只列了 `skill/github`；
  - `SetupPlace` 是 `'deployment' | 'github' | 'feishu'`；
  - `setupView` 读的是 `resolved.github.login`。
- worker 子进程由 DSH 启动，DSH 会剔除名字像凭据的环境变量（`KEY|PASSWORD|SECRET|TOKEN`）。因此凭据不能经环境变量传给 worker，只能放在文件里，由 shim 读取。
- Gerrit 3.10 的 REST 约定：
  - 用 `/a/` 前缀加 HTTP Basic 认证（HTTP 密码）；
  - 响应以 `)]}'` 开头，需去掉后再解析；
  - `ReviewInput.tag` 以 `autogenerated:` 开头表示机器消息；
  - change message 里的提及会内联为 `<GERRIT_ACCOUNT_id>`，并附带 `accounts_in_message`；
  - inline 回复通过 `CommentInput.in_reply_to` 指定；
  - 可以用 `after:"<时间>"` 查询变动过的 change。

## Goals / Non-Goals

**Goals:**
- 新增一个 `Forge` 接口，把上面列出的 GitHub 耦合全部收进去。通用代码只通过当前 forge 调用这些能力。
- GitHub 实现只搬家、不改行为。用渲染 prompt 的快照和现有测试作为回归保护。
- Gerrit 实现覆盖四份 spec 的全部要求。

**Non-Goals:**
- 不让一个部署同时使用多个 forge，也不预留多 forge 的数据结构。
- 不改核心领域模型、SQLite schema 和 KV 格式。
- 不支持 Gerrit SSH（`stream-events`、ssh push）。不对接 Gerrit Checks API，不处理默认分支的 CI。
- 飞书项目 Source 不在本次范围，另起一个 change。

## Decisions

### D1. Forge 是 Source 之外的第二个插件接口，由 Source 插件注册

```ts
interface Forge<A = unknown> {
  kind: 'github' | 'gerrit'
  source: string                                // 对应 Source kind id，也是 SetupPlace
  resolve(machine, config, probe): Promise<ForgeAccount & { detail: A }>
  environment: { shims(detail): Shim[]; gitConfig(detail): string[]; verify(detail, subprocess, signal): Promise<void> }
  review: {
    param: { name: 'pr_number' | 'change_number'; describe(account): string }
    claim(ctx: SourceContext, ticketId, number, signal): Promise<string | undefined>   // 拒绝原因或 undefined
    of(ticket): number | undefined                                                       // 卡片上的编号
    endNotices(ticket, request, account): OutboundMessage[]
  }
  readPath(commands, path, kind: 'file' | 'directory'): Promise<string>
  resource: { prefix: string; read(commands, resource): Promise<unknown> }
  skill: { name: string; content: string }
  words: Record<'review' | 'reviews' | 'forge' | 'cli' | …, string>   // prompt 用词
}
interface ForgeAccount { kind; login: string; email: string; repository: string; web: string; id?: number }
```

- GitHub Source 插件和 Gerrit Source 插件各自调用 `orchestrator.forges.register(forge)`，与 `sources.register(kind)` 并列。
- Runtime 按插件配置 `forge` 取出当前 forge。

**为什么不直接扩展 `SourceKind`：** Source 描述的是"一条消息流"，飞书和将来的飞书项目都不需要上面这些能力。如果塞进 `SourceKind`，就会多出一堆可选字段，而通用代码仍然得判断"哪个 Source 是托管"。

**为什么不把 forge 实现放在主插件里：** 各 forge 的代码本来就在 `src/sources/github*.ts` 中，并且依赖 SourceContext。放到 Source 插件里注册，GitHub 的代码基本不用挪位置，也符合 "`src/sources` 不 import `src/app`" 的依赖规则。

**为什么由主插件的配置指定 forge，而不是"哪个 Source 启用就用哪个"：** setup 在 Source 插件注册之前就要运行，并且需要确定的输入。显式配置也让"选了 Gerrit 却没启用插件"可以被检测出来，见 forge-selection spec。

### D2. setup 只依赖 forge 的纯函数，不依赖插件是否已注册

`resolve`、`environment` 等函数放在 `src/forge/github.ts` 和 `src/forge/gerrit.ts`，由主插件直接 import，形成一张静态表 `FORGES`。Source 插件注册时只把同一个对象挂到 SourceContext 能取到的地方。

这样 setup 可以在 Source 插件加载之前完成。插件未注册的问题由 Runtime 在 `ready` 之后检查，并报告到 `runtime` 健康项。

**备选方案：** 等插件注册以后再运行 setup。这需要改 Cordis 的启动顺序，而且插件被禁用时 setup 会一直挂起，所以不采用。

### D3. `Deployment` 改为通用账号结构，GitHub 字段保留为派生只读字段

```ts
interface Deployment extends Machine {
  forge: ForgeAccount & { detail: unknown }
  repository: string        // = forge.repository，供现有调用方和 ChannelLinks 使用
  github?: { cli; login; noreply }   // 仅 forge=github 时存在
  feishu?: FeishuBot
}
```

`github` 改为可选字段。TypeScript 会标出每一个直接读取 `deployment.github` 的地方，逐个改成读 `deployment.forge` 或当前 forge 的 detail。GitHub Source 内部可以继续用 `github!`，因为 GitHub Source 只在 `forge=github` 时轮询。

**BREAKING（内部）：** 第三方 Source 插件读取 `deployment.github` 的地方需要处理 `undefined`。

### D4. Commands 的传输按 forge 分开

- `Commands.api` 和 `Commands.pages` 保留原名和原签名，作为 GitHub 专用接口，内部断言 `forge=github`，这样 GitHub 代码不用改。
- 新增 `Commands.gerrit<T>(schema, method, path, body?)`，直接在宿主进程里用 `node:https` 发请求：
  - 认证用 Basic auth，凭据读自 netrc 文件，每次请求时读取，这样运维改密码后不必重启；
  - 证书校验使用可选的 CA 文件；
  - 去掉响应开头的 `)]}'`；
  - 失败时抛出 `CliError`，`code` 为 HTTP 状态码。这样现有的 410/404 判断习惯可以沿用。
- 路径限制与 GitHub 一致：拒绝绝对地址和含 `..` 的路径。
  - project 级路径会自动加上 `projects/<encoded project>/` 前缀；
  - change 级路径用 `changes/<project>~<number>`，避免不同 project 的同号冲突。

**为什么宿主不调用 worker 用的 `gerrit` 命令：** 宿主的轮询频繁，在进程内请求更省资源，也省掉每次启动子进程和解析输出的开销。worker 用的命令和宿主共用同一个模块里的请求代码，规则只有一份。

### D5. worker 的 `gerrit` 命令是打包进 bundle 的 Node 脚本

- tsdown 额外产出 `lib/gerrit-cli.js`，带 `#!/usr/bin/env node`。
- `writeEnvironment` 在 `worker-bin/gerrit` 写一个 shim，内容为 `exec node <lib/gerrit-cli.js> --config <stateDir>/gerrit.json "$@"`。
  - `gerrit.json` 只含服务器地址、project、凭据文件路径和 CA 文件路径，不含密码；
  - Node 的路径在 setup 时取 `process.execPath` 的绝对路径。
- 子命令：
  - `gerrit api [-X METHOD] [-d JSON|@file] <path>`，供 worker 调用；
  - `gerrit credential get|store|erase`，按 git credential helper 协议工作。只有 `get` 在主机和协议匹配时输出用户名和密码；`store` 和 `erase` 什么也不做；
  - `gerrit push [--branch <b>] [--remote <r>]`，上传前补全 Change-Id 后再推送，见 D6。
- 在 git 配置中只写 `[credential "<服务器 origin>"] helper = <shim> credential` 和 `useHttpPath = false`，并像 GitHub 一样先清空全局 helper。CA 文件写成 `[http "<origin>"] sslCAInfo = <file>`。git 配置中不写任何 hook 相关的设置。

**备选方案：**
- 让 worker 自己用 curl 加 `--netrc-file`：这会把密码文件路径暴露给 worker 的 prompt，worker 也可能把文件内容 cat 出来；
- 打包 git-credential-store 的文件：格式不同，而且仍然暴露密码文件。

用 shim 包一层，并不能防止 worker 读取凭据文件，因为 worker 和宿主是同一个 OS 用户。这与现有 GitHub 方案的限制相同，见 `environment.ts` 的文件头注释。凭据文件的路径不出现在任何 prompt 或环境变量中。

### D6. Change-Id 在上传前由 `gerrit push` 补全，不接入任何 hook

要求是不影响仓库自带的 hook。所以 dsh-superagent 不设置 `core.hooksPath`，也不在工单目录写入 hook。Change-Id 只在上传前检查和补全。

**官方脚本**
- 把 Gerrit stable-3.10 分支的 `resources/com/google/gerrit/server/tools/root/hooks/commit-msg` 原样放进包里，路径为 `vendor/gerrit/commit-msg`，保留 Apache-2.0 版权头，并在同目录的 README 中记录来源 commit。
- 它只作为普通脚本调用：`sh vendor/gerrit/commit-msg <消息文件>`。脚本从当前 git 环境读取 HEAD 和提交者身份，用来计算随机值。

**`gerrit push` 的步骤**
1. 确定目标分支、远端名和推送地址（见 D6a）。
2. 拉取：执行 `git fetch <远端名或推送地址> refs/heads/<branch>`，从 `FETCH_HEAD` 得到 `base`。不更新任何远端跟踪分支，避免改动仓库的远端状态。
3. 列出待上传提交：`git rev-list --reverse --topo-order HEAD --not <base>`。列表为空时报错退出。
   - 其中有合并提交时报错退出。这一版不处理合并提交，因为 worker 的工作流是在目标分支上线性提交。
   - 目标分支在远端前进、HEAD 落后于它时，不要求先 rebase，因为 Gerrit 只按这组提交创建 change。是否 rebase 交给评审者和 Gerrit 的 submit 策略。
4. 检查 Change-Id：对每个提交用 `git interpret-trailers --parse` 看是否已有 `Change-Id: I[0-9a-f]{40}`，或者已有 `Link: <url>/id/I[0-9a-f]{40}`。仓库设置了 `gerrit.reviewUrl` 时，官方脚本写的是后一种，Gerrit 同样接受。全部都有时直接执行第 6 步。
5. 补写，从第一个缺 Change-Id 的提交开始逐个处理，不经过 `git commit`，因此不会触发任何 hook：
   - 缺 Change-Id 的提交：把提交说明写入临时文件。设置 `GIT_COMMITTER_NAME/EMAIL/DATE` 为原提交的值，然后在工单目录中运行官方脚本。
     - 脚本只读取 HEAD 和提交者身份来计算随机值，并对临时文件调用 `stripspace` 和 `interpret-trailers`，不写仓库，也不碰工作区和 index。
     - 随机值的输入包含提交者身份、时间和说明，所以每个提交的 Change-Id 不同。如果同一批里仍出现重复的 Change-Id（说明和时间完全相同的提交），报错退出，不推送。
   - 写回新提交：用 `git commit-tree <原 tree> -p <新父提交> -F <消息文件>`，并设置 `GIT_AUTHOR_*` 和 `GIT_COMMITTER_*` 为原值。
   - 已有 Change-Id 的提交：如果它的父提交被改写过，用同样的 `commit-tree` 重新生成，提交说明不变；如果父提交没变，原样保留。
   - 全部完成后，用 `git update-ref -m "gerrit push: add Change-Id" refs/heads/<当前分支> <新 HEAD> <旧 HEAD>` 更新本地分支。这是带旧值检查的原子更新。分离 HEAD 时改用 `git update-ref HEAD`。
   - 输出 `<旧 sha> -> <新 sha>` 列表。
6. 推送：执行 `git push <远端名或推送地址> HEAD:refs/for/<branch>%topic=<DSH_SUPERAGENT_NAME>`。远端本身可用时传远端名，只有改用 HTTPS 时才传地址，这样 pre-push hook 收到的参数与人平时推送时一致。这是普通 push，仓库的 pre-push hook 照常运行。`DSH_SUPERAGENT_NAME` 取自执行环境，worker 也可以用 `--topic` 指定。

**官方脚本没有加 Change-Id 时（`gerrit.createChangeId=false`，或 `fixup!`、`squash!` 提交）：** 报错退出，不推送。这与官方行为一致，不强行绕过仓库的设置。

**备选方案：**
- 用 `core.hooksPath` 加转发脚本：会改变仓库 hook 的查找方式，与"不影响仓库 hook"的要求冲突。
- 让 prepare 命令安装官方 hook：会写入工单目录的 `.git/hooks`，可能覆盖仓库自己的 commit-msg hook。
- 用 `git rebase --exec`：会触发 post-rewrite 等 hook，还会动到工作区，失败时状态也不好恢复。

用 `commit-tree` 只操作对象和 ref，不碰工作区和 index，也不触发 hook。失败时本地分支保持原样。

**prompt 要求：** worker 上传评审时只用 `gerrit push`，不用仓库自带的 push 脚本（`git-push.sh`、`yarn push`、`pnpm push`、`rush push` 等）。prompt 和 skill 都写明这一点，但不禁止直接 `git push`。直接推送缺少 Change-Id 的提交时，Gerrit 服务器会拒绝，worker 看到错误后改用 `gerrit push` 即可。

不调用仓库自带 push 脚本的原因：
- 脚本自己执行 push，会绕过 `gerrit push` 的远端核对、Change-Id 补全和工单 topic；
- 脚本常写死 SSH 地址或其他远端，而智能体只有 HTTPS 凭据；
- 脚本是仓库里的任意代码，可能等待输入。

仓库定制的 push 脚本（例如按分支拼接 reviewer 邮箱）这一版不兼容。仓库的 pre-push hook 照常运行；只写在脚本里的检查，由团队写进"交付要求"，worker 在上传前执行。

### D6a. 推送目标与远端

`gerrit push` 只从命令参数、当前分支的跟踪关系和 Gerrit 获取推送目标，不读取仓库里的推送配置文件（如 `.gitreview`），也不调用仓库自带的 push 脚本。以后需要兼容某种仓库约定时，再单独加。

**目标分支**：取值顺序见 gerrit-worker-environment spec。读跟踪分支用 `git rev-parse --abbrev-ref --symbolic-full-name @{upstream}`，只在它所在的远端指向配置的 Gerrit 时采用。最后一级用 REST `projects/<p>/HEAD`。

**远端解析**
- 用 `git remote get-url --push <name>` 读取推送地址，然后解析主机和路径。路径会去掉 `/a/` 前缀和 `.git` 后缀；SSH 地址支持 `ssh://user@host:port/path` 和 `user@host:path` 两种写法。
- 主机和 project 与配置一致：HTTPS 地址直接使用；其他协议的地址改用配置的 HTTPS 地址，并输出一行说明。
- 远端不存在时：来自 `--remote` 参数就报错，否则改用配置的 HTTPS 地址。
- 主机或 project 不一致时，拒绝执行。
- 改用 HTTPS 时，直接把地址传给 `git fetch` 和 `git push`，不调用 `git remote add` 或 `set-url`，所以不改动仓库配置。git 的 credential helper 按 origin 匹配，这个地址同样能取到凭据。

**为什么地址总是取 Gerrit Source 的配置：** 仓库里的远端或文件不能决定凭据发往哪台主机；仓库远端用 SSH 时也能用智能体的 HTTPS 凭据上传。

### D7. Gerrit Source 的轮询

每一轮按以下顺序执行，每一步单独计算失败：

1. **增量查询**：`changes/?q=project:<p> after:"<游标>"&o=MESSAGES&o=DETAILED_ACCOUNTS&o=CURRENT_REVISION&o=DETAILED_LABELS`，分页用 `S=` 加 `_more_changes`。
   - 游标的推进方式与 GitHub 相同：退到最新 `updated` 之前 5 秒，并用 `POLL_HORIZON_MS` 限制最远回看范围。
   - 去重靠 Trigger id：
     - change message 用 `key('gerrit-message', change, message.id)`；
     - inline comment 用 `key('gerrit-comment', change, comment.id)`；
     - 新 change 用 `key('gerrit-change', change)`。
2. **筛选接收范围**：对查询到的每个 change，按 gerrit-source spec 的"接收范围"判断。
   - 判断智能体是否相关时，读 `reviewers`、`owner` 和 `attention_set`；
   - 还会检查消息里是否点名智能体。点名会让 Gerrit 把智能体加为 CC，但新加的 CC 有时晚一轮才可见，所以也直接检查消息文本。
3. **读取评论**：对接收的 change，读 `changes/<id>/comments`。只取 `updated` 不早于该 change 游标（`KV.gerrit.cursor(n)`）的评论，转成 inline Trigger。
4. **处理工单绑定的 change**：
   - 用状态更新 follows：MERGED 报 merged，ABANDONED 报 closed，NEW 时如果曾经关闭过就重新跟随；
   - 执行自动认领；
   - 更新 Thread 上 `Verified` 和 `Code-Review` 的汇总；
   - 投票不需要单独比较：它们随 change message 到达，按消息的发送者判断是人还是机器人。目前 CI 机器人已下线，`Verified+1` 由员工手动投，按人的消息送达 worker。以后 CI 恢复，只需把 CI 账号加入机器人名单。
5. **轮询订阅的 Thread**：对本轮没读到的已订阅 Thread，复用 `pollThreads` 补读。

**为什么不用 `attention:self` 或 `cc:self` 做主查询：** 被点名后才加 CC，而点名之前的消息也需要作为上下文。用 project 范围的 `after:` 查询一次就能覆盖全部情况。按 Gerrit 文档，`after:` 匹配的是 change 的修改时间，任何新消息都会更新它。

**为什么不用 `stream-events`：** 它需要 SSH 和 `Stream Events` 权限。轮询加 Trigger 去重与 GitHub 的模型一致，重启也不会丢事件。

### D8. 回复去重用 `tag`

- 回复时调用 `POST changes/<id>/revisions/current/review`，请求体为 `{ message | comments, tag: 'dsh-superagent:<message.id 前 32 位>', notify: 'OWNER_REVIEWERS', omit_duplicate_comments: true }`，不带 `labels`。
- 发送前先读 `changes/<id>/messages`，以及 inline 回复所在的 `comments`。如果已有智能体发出、`tag` 相同的条目，直接返回已发送。

**为什么用 `tag` 而不像 GitHub 那样在正文里加 HTML 注释：** Gerrit 的评论按 Markdown 渲染，HTML 注释会显示为纯文本。

**为什么 tag 不以 `autogenerated:` 开头：** 带这个前缀的消息会被 Gerrit UI 的"只看人的评论"过滤隐藏，人就看不到智能体的回复。Gerrit 允许任意 tag，`autogenerated:` 只是 UI 的约定。智能体自己的消息在轮询时按账号 id 过滤，不依赖 tag。

### D9. 评审单绑定复用 `follows`，规则写在 `src/sources/gerrit-change.ts`

结构与 `github-pull.ts` 对称：`readChange`、`claimChange`、`observeChange`、`changesOf`、`changeEndNotices`。

"自己的 change"判断如下：当前 patchset 的 `uploader._account_id` 等于智能体 id，`project` 等于配置的 project，且 `topic === ticket.execution.name`。topic 必须完全匹配。GitHub 用的是"分支名最后一段"，因为 Gerrit 的 topic 本身就是一个独立字段，没有路径层级。

change 被 abandon 后又 restore，复用现有 "closed follow 再次 open" 的逻辑。

### D9a. 仓库读取用 Gerrit REST 加 gitiles

公司实例已经安装 gitiles 3.10.0。

- 读文件：`projects/<p>/branches/<HEAD 分支>/files/<path 编码>/content`，返回 Base64，解码后得到内容。这是 Gerrit 核心 REST 接口。
- 列目录：`plugins/gitiles/<p>/+/refs/heads/<分支>/<path>?format=JSON`，返回 `entries`，包含名称、类型和 mode。请求同样走 `/a/` 和 Basic auth，由 `Commands.gerrit` 统一处理，去掉 `)]}'` 前缀的规则同样适用。
- gitiles 返回 404，而对应路径确实是目录时（例如插件被卸载），报明确的错误，提示 worker 在工单目录中直接查看。不回退到其他方式。

### D10. prompt 按 forge 选文件，GitHub 渲染结果作为快照

（实现时由"模板词替换"改为"按 forge 选文件"，理由见下。）

- `prompts/*.md` 和 `prompts/team/*.md` 保持原样，就是 GitHub 的文本。`tests/github-baseline.spec.ts` 的快照保证 GitHub 部署的渲染结果逐字不变。
- Gerrit 的文本放在 `prompts/forge/gerrit/` 下同名的文件里，例如 `prompts/forge/gerrit/work.md`。`promptFile(name, forge)` 在该 forge 有同名文件时读取它，否则读取通用文件。只有含托管用词的文件才需要 Gerrit 版本；不含的文件（如 `shared.md`、`admission.md`）两个 forge 共用。
- 内置 part（`builtInParts`）、团队默认段（`teamDefaults`）、内置 skill 都按 forge 生成。键名保持不变，只有 skill 的键按 forge 不同：GitHub 部署为 `skill/github`，Gerrit 部署为 `skill/gerrit`。团队保存的覆盖内容按键生效，所以 GitHub 部署保存过的 `skill/github` 覆盖在 Gerrit 部署中不生效，面板也不显示。
- Gerrit 的文本描述 Gerrit 工作流：一律用 `gerrit push` 上传；修改时 amend 同一个提交，保留 Change-Id；回复评论线程并标记 resolved；不投票，不 Submit，不新开 change。

**为什么不用占位符替换：** 需要改的托管句子约有 60 处，分布在 14 个文件里。其中多数在 Gerrit 下不是换一个词，而是整句含义不同，例如 auto-merge、review 线程、分支认领、`Co-authored-by` 改写分支。用占位符会让 GitHub 文本里混入大量 `{review}`，读起来困难，替换后也很难保证逐字一致。按文件覆盖时，GitHub 文本不动，Gerrit 文本自然通顺。

**代价：** 通用规则改动时，需要同时改 Gerrit 版本。`tests/gerrit-prompts.spec.ts` 会检查两点：每个 Gerrit 文件都有对应的通用文件；Gerrit 渲染结果中不出现 `gh `、`PR`、`pull request`、`pr_number`、`GitHub` 等 GitHub 用词。

**备选方案：** 维护两套完整的 prompt 目录。相比只覆盖需要的文件，它会复制所有与托管无关的文件，所以不采用。

### D11. KV、SetupPlace、健康项

- `KV.gerrit`：`since`、`cursor(n)`、`retries`，与 `KV.github` 对称，前缀为 `gerrit-`。不需要 CI 指纹，因为投票随消息到达，见 D7。
- `SetupPlace` 增加 `'gerrit'`。setup 错误码增加 `gerrit*` 系列，包括无法登录、无用户名或邮箱、project 不可读、无上传权限、凭据文件、证书。选中 forge 的 Source 被关闭不算 setup 问题，与 GitHub 的现有行为一致；插件未注册由 `runtime` 健康项报告。
- `HealthCode` 增加 `notForge`，表示"未被选为代码托管"。
- `SETUP_FIELDS` 增加 `gerrit: ['url', 'project', 'netrc', 'ca']`。`setupChanged` 只比较选中 forge 的字段和 feishu 的字段。

## Risks / Trade-offs

- **[风险] 抽象层把 GitHub 行为改坏了** → 先把 GitHub 渲染的 prompt 存为快照，再动代码。现有 95 个测试文件必须全部通过。第一组任务只做搬家，不加 Gerrit。
- **[风险] `after:` 查询在大 project 上很慢，或返回数量受 `queryLimit` 截断** → 分页循环直到 `_more_changes` 为假。若某轮请求被限流，游标不前进，并在健康详情中报告。首轮只查 `POLL_HORIZON_MS` 以内的变动。
- **[风险] 时间格式和时区** → Gerrit 返回的是 UTC，格式为 `2026-11-12 08:00:00.000000000`。统一转换成 ISO 字符串，查询时以 `"YYYY-MM-DD HH:MM:SS"` 加上 UTC 发送。为此写一个往返测试。
- **[风险] `gerrit push` 改写了 worker 的本地提交** → 只改写缺 Change-Id 的提交及其后代；用 `update-ref` 加旧值检查做原子更新；输出旧 sha 到新 sha 的对照；不碰工作区和 index。合并提交和非线性历史直接报错，不尝试改写。
- **[风险] 仓库自带 push 脚本里有 pre-push hook 之外的必要逻辑** → `gerrit push` 不调用这些脚本（见 D6），例如按分支自动添加 reviewer 的逻辑不会生效，评审者需要人在 Gerrit 上添加。检查类步骤由团队写进"交付要求"。部署文档提醒团队检查一遍自己的 push 脚本。
- **[风险] worker 绕过 `gerrit push`，直接 `git push`** → 缺 Change-Id 的提交会被 Gerrit 服务器拒绝（project 要求 Change-Id 时），worker 改用 `gerrit push` 即可；topic 缺失时可以由自动认领兜底，但前提是 topic 正确，所以 prompt 要求一律使用 `gerrit push`。
- **[风险] worker 和宿主是同一个 OS 用户，worker 仍可读到凭据文件** → 这与 GitHub 方案的限制相同。凭据文件路径不进入 prompt 或环境变量，setup 还检查文件权限为 0600。文档建议使用专用的服务账号，并只授予 project 的 Read 和 Push to `refs/for/*` 权限，不授予 Submit 和 Label。
- **[取舍] 智能体的回复不带 `autogenerated:` 前缀** → 人在 UI 中能看到回复，代价是智能体的评论会出现在"人类评论"视图中。账号本身可以标记为 `SERVICE_USER`，以便区分。
- **[取舍] 不支持默认分支 CI 和 Checks API** → Gerrit 部署下，接收表没有 CI 一行。目前公司 CI 机器人已下线，由员工手动投 `Verified`，这些投票作为人的消息送达。如果以后需要，再单独扩展。
- **[风险] 以前的 CI 投票用的是员工个人账号** → 这类投票会被当作人的消息，可以唤醒已结束的工单，名单上的员工还能借此发起工作。CI 恢复时，建议改用单独的服务账号，并标记为 `SERVICE_USER`，或者加入机器人名单。部署文档会写明这一点。

## Migration Plan

1. 先合入"抽象层加 GitHub 实现"。现有部署无需任何操作，`forge` 默认为 `github`。回滚只需回退代码，数据不受影响。
2. 再合入 Gerrit 实现。启用步骤写入 `docs/006-deployment.md`：
   - 在 Gerrit 上创建服务账号，给 project 授予 Read 和 Push `refs/for/*` 权限，生成 HTTP 密码；
   - 编写 netrc 文件，权限设为 0600，如有需要准备 CA 文件；
   - 在 profile 中设置 `dsh-superagent.forge: gerrit`，启用 `dsh-superagent-gerrit`，可以禁用 `dsh-superagent-github`；
   - 在面板的 Gerrit Source 中填写地址、project、凭据文件和 CA 文件，保存后会自动重启；
   - 把 prepare 命令改为从 Gerrit clone 的本地仓库添加 worktree，示例写在文档里。
3. 回滚：把 `forge` 改回 `github`，或者禁用 Gerrit 插件。已有的 `gerrit:` Thread 和 KV 记录保留，不影响 GitHub。

## Open Questions

- Gerrit 实例的 `index.maxLimit` 或 `queryLimit` 是多少：只影响分页大小的默认值，可以在部署时调整。
- 当前 project 是否要求 Change-Id（`receive.requireChangeId`）：只影响 worker 直接 `git push` 时的报错方式，不影响 `gerrit push`。
