## Purpose

规定 Gerrit 作为 dsh-superagent 的来源和回复渠道时的行为：接收哪些事件、什么算点名、谁算人、投票如何到达工单、change 结束如何结束工单、回复如何发出且不重复。

## ADDED Requirements

### Requirement: Gerrit Source 的配置
Gerrit Source SHALL 接受以下配置：
- 服务器地址：`https://` 开头，可带路径前缀；
- 一个 project 名；
- 凭据文件的绝对路径；
- 可选的 CA 证书文件绝对路径：服务器使用公司自签证书时，宿主的请求和 worker 的 git 都用它校验证书；
- 轮询间隔：60 到 3600 秒，默认 60；
- 连续失败多少次后报告异常：1 到 20，默认 3；
- 开关"接收 project 里的新 change"，默认关；
- 开关"接收 project 里的评论"，默认关。

服务器地址、project、凭据文件和 CA 文件 SHALL 属于 setup 字段：保存时检查账号，检查通过后重启 dsh-superagent，与 GitHub Source 的仓库和 CLI 字段一致。

#### Scenario: 非 https 地址
- **WHEN** 服务器地址填写 `http://gerrit.example.com`
- **THEN** 保存被拒绝，并提示地址必须使用 https

#### Scenario: 自签证书
- **WHEN** 服务器使用公司 CA 签发的证书，且 CA 文件已配置
- **THEN** setup 检查、轮询、回复和 worker 的 `git push` 都能校验通过；未配置 CA 文件时，setup 问题指出证书无法校验

#### Scenario: 修改 project
- **WHEN** 人在面板把 project 从 `a` 改为 `b` 并保存
- **THEN** 系统检查智能体账号能否读取并上传到 `b`；通过则保存并重启，不通过则拒绝保存并显示原因

### Requirement: 接收范围
Gerrit Source SHALL 接收配置 project 中以下 change 上的活动：
- 智能体是 owner、reviewer、CC 或在 attention set 中的 change；
- 已有工单订阅的 change；
- "接收新 change"打开时，打开开关之后新建的 change；
- "接收评论"打开时，所有 change。

其他 project 的活动 SHALL NOT 被接收。智能体账号自己写的消息和评论 SHALL NOT 成为 Trigger。

#### Scenario: 别人 @ 智能体
- **WHEN** 有人在 project 内某个 change 的回复里写 `@agent-bot 请修一下`，Gerrit 因此把智能体加为 CC
- **THEN** 下一轮轮询把这条回复作为该 change Thread 上的 Trigger 收入

#### Scenario: 其他 project
- **WHEN** 智能体被加为另一个 project 中 change 的 reviewer
- **THEN** 该活动不被接收

#### Scenario: 智能体自己的回复
- **WHEN** 轮询读到智能体账号发出的 change message
- **THEN** 不产生 Trigger

### Requirement: Thread 和 Trigger 的划分
每个 change SHALL 是一个 Thread，键为 `gerrit:<change 编号>`。下列内容 SHALL 各成为一个 Trigger，并且只收入一次：
- 新建 change 的标题和提交说明；
- 每条 change message，包括随消息投出的票；
- 每条已发布的 inline comment。

同一条消息在后续轮询中再次读到时 SHALL 被识别为重复，不会再次进入评估。

#### Scenario: 重复读取
- **WHEN** 由于轮询游标回退，同一条 change message 在两轮轮询中都被读到
- **THEN** 第二次接收返回 duplicate，不产生新的评估

#### Scenario: inline comment 的位置
- **WHEN** 有人在 patchset 3 的 `src/a.ts` 第 42 行留下 inline comment
- **THEN** Trigger 文本包含文件路径和行号，元数据记录 patchset、路径、行号和评论 id

### Requirement: 点名和发送者类型
Trigger 中出现以下任一情况时，SHALL 被标记为点名智能体：
- 包含 `@<智能体用户名>` 或 `@<智能体登记邮箱>`，不区分大小写，且前后不与用户名字符相连；
- Gerrit 在消息中把提及的账号内联为 `<GERRIT_ACCOUNT_<id>>` 形式，且 id 是智能体的账号 id。

下列消息 SHALL 视为非人：
- 带 `autogenerated:` 前缀 tag 的消息，例如上传 patchset 的系统消息，以及以这类 tag 投票的机器人；
- 账号带 `SERVICE_USER` 标签的作者；
- 策略机器人名单上的账号。

非人消息 SHALL NOT 发起明确请求，也 SHALL NOT 唤醒已结束的工单。

#### Scenario: 邮箱点名
- **WHEN** 名单上的用户写 `@Agent-Bot@example.com 帮忙看下`，智能体登记邮箱为 `agent-bot@example.com`
- **THEN** 该 Trigger 被视为点名智能体的明确请求候选

#### Scenario: 上传 patchset 的系统消息
- **WHEN** 已结束工单订阅的 change 上，有人上传了新 patchset，Gerrit 生成 `autogenerated:gerrit:newPatchSet` 消息
- **THEN** 该 Trigger 为非人，不唤醒已结束的工单

### Requirement: 策略中的 Gerrit 部分
Gerrit Source 的策略部分 SHALL 包含：
- 能发起工作的 Gerrit 用户名名单；
- 消息可以成为推断候选的机器人用户名名单。

接收表 SHALL 有两行："新 change"和"评论"。打开对应开关时，接收不点名的内容；关闭时只接收点名智能体的内容。

#### Scenario: 名单外的人点名
- **WHEN** 不在名单上的用户 @ 智能体
- **THEN** 按接收表"名单外、点名"一格的设置处理，与 GitHub Source 的同名格行为相同

### Requirement: 投票
change message 中带有的投票（如 `Code-Review+2`、`Verified+1`、`Verified-1`）SHALL 写入该消息 Trigger 的文本，并在元数据中记录标签、分值和 patchset。投票的发送者按"点名和发送者类型"判断：
- 人投的票与人的消息相同，即使消息没有文字，也 SHALL 送达工单。这与 GitHub 中没有正文的 review 决定一致，worker 可能正在等待这次人工 Verify。
- 带 `autogenerated:` 前缀 tag 的投票，或机器人名单上账号投的票，属于非人消息。

系统 SHALL NOT 另外合成没有发送者的 CI Trigger。已绑定 change 的 Thread SHALL 显示当前 patchset 上 `Verified` 和 `Code-Review` 的汇总。

#### Scenario: 人工 Verify
- **WHEN** 工单绑定的 change 当前 patchset 上，某位员工投了 `Verified+1`，没有写文字
- **THEN** 该 change 的 Thread 上出现一条 Trigger，内容说明谁在第几个 patchset 投了 `Verified+1`，作为人的消息送达工单的 worker；Thread 上的 Verified 汇总更新

#### Scenario: 机器人投票
- **WHEN** 机器人名单上的账号在已结束工单所绑定的 change 上投了 `Verified-1`
- **THEN** 该 Trigger 为非人，不唤醒已结束的工单

### Requirement: change 结束
Gerrit Source 读取到工单所跟随的 change 状态变为 `MERGED` 时，SHALL 以 `merged` 报告该 Thread 关闭；状态变为 `ABANDONED` 时，SHALL 以 `closed` 报告。被 abandon 后又 restore 的 change SHALL 重新成为打开状态，并由原工单继续跟随。

#### Scenario: change 合并
- **WHEN** 工单自己上传的 change 被人 Submit，状态变为 `MERGED`
- **THEN** 工单按现有规则以 merged 结束，订阅保留

#### Scenario: restore
- **WHEN** 工单跟随的 change 被 abandon，之后又被 restore
- **THEN** 该 change 对工单重新打开，工单可以继续跟随它

### Requirement: 回复渠道
Gerrit Source 的回复 SHALL 以智能体账号通过 review 接口发出，不投任何票：
- 回复 inline comment 时，SHALL 作为该评论所在 patchset、文件和行的回复，回复对象为该评论；
- 其他回复 SHALL 作为 change 当前 patchset 上的消息；
- 在已合并或已 abandon 的 change 上，回复仍然发出。

同一回复因重试被发送多次时，change 上 SHALL 只出现一条，判断依据是回复附带的、不写在正文里的标识（不依赖正文标记）。change 不存在且确认已删除时，SHALL 返回 gone；其他失败 SHALL 让发件箱重试。

#### Scenario: 回复 inline comment
- **WHEN** 工单回复一条位于 patchset 2 `src/a.ts:10` 的 inline comment
- **THEN** 回复出现在同一位置，作为该评论线程的下一条，且没有改变任何投票

#### Scenario: 重试不重复
- **WHEN** 一次回复已发出，但网络超时，发件箱在 5 秒后重试
- **THEN** 重试发现同一标识的消息已存在，返回已发送，change 上只有一条回复

### Requirement: 链接与搜索
回复渠道的链接 SHALL 指向 Gerrit 网页上的 change，inline 回复链接到该评论。搜索时 SHALL 识别以下形式并找到对应的 change Thread：`12345`、`#12345`、`<服务器地址>/c/<project>/+/12345`，以及 `<服务器地址>/12345`。

#### Scenario: 粘贴 change 链接搜索
- **WHEN** 人在面板搜索框粘贴 `https://gerrit.example.com/c/widgets/+/12345/3`
- **THEN** 结果包含 Thread `gerrit:12345`

### Requirement: 轮询失败与健康
Gerrit Source SHALL 用健康项 `gerrit` 报告状态。连续失败次数达到配置的阈值后，SHALL 报告错误；更少的失败 SHALL 保持安静，并在下一轮重试。单个 change 读取失败 SHALL NOT 阻止同一轮里其他 change 的读取。持续失败超过 24 小时的单个 change SHALL 停止重试，并在健康详情中列出。

#### Scenario: 一次网络中断
- **WHEN** 阈值为 3 时，一轮轮询因网络中断失败
- **THEN** 健康项不变为错误，下一轮照常轮询

#### Scenario: 凭据失效
- **WHEN** 智能体的 HTTP 密码被重置，连续 3 轮轮询都返回 401
- **THEN** 健康项变为错误，详情包含 401 和失败次数
