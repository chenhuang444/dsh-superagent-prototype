---
name: dsh-superagent-gitlab
description: Read and answer GitLab issues, merge requests, discussions and pipelines using glab.
---

Workers use orchestrator_read for project context when needed: gitlab/issues/<iid> or gitlab/merge_requests/<iid> for the description; gitlab/issues/<iid>/notes/1 or gitlab/merge_requests/<iid>/notes/1 for its notes, including diff notes; gitlab/merge_requests/<iid>/discussion/<discussion-id> for one discussion with all its notes; gitlab/merge_requests/<iid>/pipelines for the MR's pipeline jobs; gitlab/commits/<sha>/pipelines for the pipelines of a commit. Issues are #<iid> and MRs !<iid>; the two number separately. A page holds 20 entries and names next_resource while another may follow. A note is `{ id, from, at, text, reply_to?, path?, line?, url }`: `id` is GitLab's note id, `reply_to` the discussion it belongs to, `path` and `line` a diff note's file and line, and `bot: true` marks a bot user, such as a project or group access token bot, whose words never authorize work. Follow next_offset to finish the current response; offset 0 reads afresh, later offsets the same snapshot. Reading does not create tickets or send replies. Allowed mentions subscribe the Issue/MR. Subscribed notes, approvals and requests for changes arrive without further mentions; MRs authored by the deployment's GitLab account from the deployment's project are subscribed automatically and changed pipelines on subscribed MRs are delivered. Other activity is available on demand; read the CLI instructions included in this skill for glab access to context beyond these shortcuts.

Before substantial work on a new human request or review note, call `orchestrator_ack` with its original trigger ID and a brief request-specific `text`, even within an existing ticket; the host replies once in that source discussion. This acknowledgement is separate from how review discussions are answered. Do not acknowledge bots or pipelines.

Answer and resolve review discussions as the Communication section says. To resolve a discussion, use `glab api -X PUT "projects/$DSH_SUPERAGENT_GITLAB_PROJECT_ID/merge_requests/<iid>/discussions/<discussion-id>?resolved=true"`.

For a note URL ending in `#note_<ID>`, read gitlab/merge_requests/<iid>/notes/1 and its next pages to find the note and its discussion, then read gitlab/merge_requests/<iid>/discussion/<discussion-id>. When the outcome requires a reply, post with `glab api -X POST projects/$DSH_SUPERAGENT_GITLAB_PROJECT_ID/merge_requests/<iid>/discussions/<discussion-id>/notes -f body=<text>`, where `$DSH_SUPERAGENT_GITLAB_PROJECT_ID` is the project id from the execution environment section. Do not use `glab mr note` or a new top-level note for review-discussion explanations. Record the bot run identifier, review-round count and dispositions in `orchestrator_report`; the MR description retains the final implementation, verification and material limitations.

The host delivers subscribed MR notes, approvals and pipelines directly to the bound worker. Immediately after creating or adopting a ticket MR, call `orchestrator_report` with `state: progress` and `mr_number`, the MR's iid; do not wait for pipelines or handoff. Read each original trigger and acknowledge new human requests before substantial work. Worker reports still go to the orchestrator for concise source-conversation delivery.
