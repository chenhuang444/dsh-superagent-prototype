---
name: dsh-superagent-gitlab
description: Read and answer GitLab issues, merge requests, discussions and pipelines using glab.
---

Workers use orchestrator_read for project context when needed: gitlab/issues/<iid> or gitlab/merge_requests/<iid> for the description; gitlab/issues/<iid>/notes/1 or gitlab/merge_requests/<iid>/notes/1 for its notes, including diff notes; gitlab/merge_requests/<iid>/discussion/<discussion-id> for one discussion with all its notes; gitlab/merge_requests/<iid>/pipelines for the MR's pipeline jobs; gitlab/commits/<sha>/pipelines for the pipelines of a commit. Issues are #<iid> and MRs !<iid>; the two number separately. A page holds 20 entries and names next_resource while another may follow. A note is `{ id, from, at, text, reply_to?, path?, line?, url }`: `id` is GitLab's note id, `reply_to` the discussion it belongs to, `path` and `line` a diff note's file and line, and `bot: true` marks a bot user, such as a project or group access token bot, whose words never authorize work; when DSH_SUPERAGENT_GITLAB_IDENTITY is personal, `agent: true` marks what the agent wrote with the account and `owner: true` what the account's person wrote. Follow next_offset to finish the current response; offset 0 reads afresh, later offsets the same snapshot. Reading does not create tickets or send replies. Allowed mentions subscribe the Issue/MR. Subscribed notes, approvals and requests for changes arrive without further mentions; MRs authored by the deployment's GitLab account from the deployment's project are subscribed automatically and changed pipelines on subscribed MRs are delivered. Other activity is available on demand; read the CLI instructions included in this skill for glab access to context beyond these shortcuts. glab is for reads; every GitLab write goes through the gitlab_* tools, which act only on this ticket's own Issues and MRs and sign what they post.

Before substantial work on a new human request or review note, call `orchestrator_ack` with its original trigger ID and a brief request-specific `text`, even within an existing ticket; the host replies once in that source discussion. This acknowledgement is separate from how review discussions are answered. Do not acknowledge bots or pipelines.

Answer and resolve review discussions as the Communication section says. To resolve a discussion, call gitlab_resolve with the MR's iid, the discussion id and resolved true.

For a note URL ending in `#note_<ID>`, read gitlab/merge_requests/<iid>/notes/1 and its next pages to find the note and its discussion, then read gitlab/merge_requests/<iid>/discussion/<discussion-id>. When the outcome requires a reply, call gitlab_reply with kind mr, the MR's iid, the discussion_id and the text. Do not post a new top-level note for review-discussion explanations. Record the bot run identifier, review-round count and dispositions in `orchestrator_report`; the MR description retains the final implementation, verification and material limitations.

The host delivers subscribed MR notes, approvals and pipelines directly to the bound worker. Open the ticket MR with gitlab_mr_create, change it with gitlab_mr_update, and close it with gitlab_mr_close. Immediately after creating or adopting a ticket MR, call `orchestrator_report` with `state: progress` and `mr_number`, the MR's iid; do not wait for pipelines or handoff. Read each original trigger and acknowledge new human requests before substantial work. Worker reports still go to the orchestrator for concise source-conversation delivery.

When DSH_SUPERAGENT_GITLAB_IDENTITY is personal, the account is a person's own: people address the agent with `$DSH_SUPERAGENT_GITLAB_TRIGGER:` at the start of a line, and a note that only @mentions the account is for that person. Never use git push options, and never enable auto-merge or merge.
